# دفتر — نظام إدارة تحصيل الديون (Daftar)

تطبيق ويب (HTML/CSS/JS بدون بناء) لإدارة المدينين والدفعات والمتابعات وعروض الأسعار، مع Supabase كقاعدة بيانات ومصادقة.
Static web app + Supabase (Auth, Postgres with Row Level Security, Storage, one Edge Function).

## ما الذي يُخزَّن على جهازك؟ لا شيء
- لا `localStorage` ولا `sessionStorage` ولا cookies ولا IndexedDB ولا service worker.
- الجلسة في ذاكرة الصفحة فقط: **تحديث الصفحة = تسجيل دخول جديد**، وتسجيل الخروج يعيد تحميل الصفحة لمسح كل شيء من الذاكرة.
- تفضيلات المظهر (اللغة، الليلي/النهاري، الثيم، البحث المحفوظ) تُحفظ **في حسابك على الخادم** (`profiles.prefs`) وتعود معك على أي جهاز.
- عند أول تشغيل يمسح التطبيق أي بقايا من النسخ القديمة في المتصفح.
- المكتبات والخطوط مستضافة داخل المشروع (`vendor/`, `fonts/`) فلا طلبات لأي CDN.

## الإعداد (أول مرة) — جرّبه على مشروع Supabase تجريبي أولًا
1. **الجداول:** شغّل `supabase/schema.sql` ثم ملفات `*-migration.sql` الأخرى (المرفقات، حقول عروض الأسعار).
2. **المصادقة:** Authentication › Providers › Email: عطّل *Confirm email* وعطّل *Allow new users to sign up*.
3. **أول مدير:** Authentication › Users › Add user: البريد `admin@daftar-auth.app` (أو نطاقك، انظر الأسفل) + كلمة مرور قوية + Auto-confirm.
4. **الأمان:** شغّل `supabase/secure-auth-migration.sql` **آخرًا**، ثم نفّذ أمر «تعيين المدير الأول» الموجود في القسم 6 من الملف.
5. **دالة المستخدمين:**
   ```bash
   supabase functions deploy admin-users
   supabase secrets set AUTH_EMAIL_DOMAIN=daftar-auth.app ALLOWED_ORIGIN=https://your-app.vercel.app
   ```
6. **الإعدادات:** حدّث `supabase-config.js` (url و anonKey). نطاق البريد `emailDomain` يجب أن يطابق `AUTH_EMAIL_DOMAIN`.
7. انشر على Vercel (`vercel.json` يضبط CSP وبقية ترويسات الأمان). بعد التأكد أن كل شيء يعمل: `drop table public.users;` (القسم 7).

> اسم المستخدم يُحوَّل داخليًا إلى بريد (`username@emailDomain`) — لا تُرسل أي رسائل بريد. أنشئ بقية المستخدمين من الإعدادات › المستخدمون (تمر عبر الدالة؛ مفتاح service_role لا يصل للمتصفح أبدًا).

## نموذج الأمان
| الطبقة | ما يحدث |
|---|---|
| المفتاح العام (anon) | لا يرى أي جدول — كل السياسات `to authenticated` |
| المدير | كل شيء + إدارة المستخدمين + مفاتيح API (الصف 2 في `app_settings`) |
| المندوب | حالات مندوبه فقط (RLS بحسب `rep_id`)، كتابة حسب صلاحياته، لا يكتب في المندوبين/الإعدادات |
| المشاهد | قراءة فقط |
| سجل التدقيق | إضافة فقط باسم المستخدم نفسه، لا تعديل ولا حذف، القراءة للمدير |
| مرفقات عروض الأسعار | مخزن **خاص** + روابط موقّعة تنتهي بعد 5 دقائق |
| المتصفح | تسجيل دخول: قفل 30 ثانية بعد 5 محاولات خاطئة (إضافة لحدود Supabase نفسها) |

## الاختبارات
```bash
npm install
npm test        # 19 اختبارًا سلوكيًا على التطبيق الحقيقي داخل jsdom مع Supabase وهمي
```
تغطي: عدم قراءة أي بيانات قبل الدخول، عدم لمس أي تخزين في المتصفح، القفل بعد المحاولات الفاشلة، المزامنة حسب الدور وعلى مستوى السجل (لا تحذف ولا تكتب فوق ما أضافه مستخدم آخر)، منع الكتابة إذا فشل التحميل الأولي، حفظ التفضيلات بالـRPC، إدارة المستخدمين عبر الدالة، الروابط الموقّعة، إمكانية الوصول، وترويسات الأمان. (سياسات RLS نفسها تُختبر على Supabase تجريبي — انظر القائمة أدناه.)

## قائمة فحص يدوي على مشروع تجريبي قبل الإنتاج
- مستخدم مندوب لا يرى حالات مندوب آخر، ولا يستطيع تعديلها عبر `curl` مباشر بمفتاحه.
- طلب بالمفتاح العام فقط (بلا تسجيل دخول) يعيد 0 صفوف من كل جدول.
- مشاهد لا ينجح في أي `insert/update/delete`.
- محاولة `update/delete` على `audit_log` تفشل.
- فتح رابط مرفق قديم (`/object/public/...`) يعيد 400/404.
